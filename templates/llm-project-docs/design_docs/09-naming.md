# 09. Именование и структура файлов

## 1. Идентификаторы

Артефакты с отдельными файлами используют последовательные идентификаторы:

- `SRC-NNN` — источник/фрагмент видения или принятое решение, если ведётся реестр источников;
- `US-NNN` — пользовательская история/сценарий;
- `REQ-NNN` — требование;
- `CON-NNN` — ограничение;
- `COMM-NNN` — коммутативная диаграмма;
- `STR-NNN` — струнная диаграмма;
- `NAV-NNN` — запись следа навигации.
- `LEG-NNN` — унаследованный компонент: код существует, но документированный контракт не извлечён; используется в `design/trace/coverage.yaml` с `disposition: not_adopted`;
- `DISC-NNN` — запись рассогласования в `design/trace/discrepancies.yaml`.

Ключи в `design/floor1/glossary.yaml` используют стабильный `snake_case` и не обязаны иметь отдельные `ENT/ROLE/ACT-NNN`. Не смешивай два формата идентификации.

## 2. Пути

```text
design/human/001-vision.md
design/floor1/glossary.yaml
design/floor1/stories/US-001.yaml
design/floor2/requirements/REQ-001.yaml
design/floor2/constraints/CON-001.yaml
design/floor2/diagrams/comm/COMM-001.yaml
design/floor2/diagrams/string/STR-001.yaml
design/trace/nav-log.yaml
design_docs/...
```

Формат конкретной записи `NAV-NNN` определён в `06-navigation.md`. `src/` и прочие инженерные директории определяются конкретным проектом; правила `design/` описывают их интерфейсы только в той мере, в какой это подтверждено требованиями.


Имена подпроектов в `subs/` совпадают с именем выделенного модуля: `subs/<module_name>/`.
## 3. Имена и ссылки

- Имена файлов — lowercase/kebab-case для правил; фиксированные идентификаторы сохраняются как есть.
- Ключи словаря — `snake_case`, английские или иные по принятому в проекте стандарту; выбери один стиль при старте и не меняй молча.
- Внутренние ссылки относительные и проверяемые. Не используй номера строк как единственную ссылку на источник.
- Ссылки на сущности, истории, требования и диаграммы используют канонические ID/ключи, не повторяют имена текстом там, где нужна машинная связь.

## 4. Статусы и приоритеты

Статусы принятия: `draft`, `confirmed`, `deprecated`. Статусы проверки задаются отдельным полем (`not_run`, `passed`, `failed`, `blocked`, `waived`). Приоритеты: `must`, `should`, `could`. `deprecated` не означает, что запись можно удалить, пока на неё есть ссылки.

## 5. Git

Один коммит — одна логическая операция, но операция может затрагивать несколько связанных файлов. Например, добавление истории вместе с новыми нужными терминами глоссария обычно является одним коммитом. Раздельные коммиты нужны, если изменения можно независимо проверить или откатить.

Git хранит диффы. След навигации фиксирует обоснование решений, причинные зависимости, конфликты, декомпозиции, смену базиса и откаты; не дублируй в нём каждый механический рефакторинг/переформатирование.

## 6. Изменение структуры

Новый файл правил добавляется только при наличии самостоятельного назначения. При перемещении файла обнови ссылки и выполни проверку. Изменения ID существующего артефакта требуют миграции ссылок, а не простого переименования.
