# 10. Рабочие маршруты и треки диалогов

Этот файл отвечает на практический вопрос: **какой маршрут выбрать, что передать LLM, какой промпт запустить и какой результат ожидать**.

## 0. Три движения и отдельный мета-трек

Любое изменение **содержания проекта** сводится к трём движениям:

| Движение | Направление | Основной трек | Когда |
|---|---|---|---|
| Сверху вниз | намерение → контракт → код | A | новый функционал, новое требование |
| Снизу вверх | код → извлечённый контракт → документация | C | существующий код без достаточной документации |
| Оценка рассогласования | документация ↔ код → список конфликтов | D | аудит, баг, drift, параллельные изменения |

Реальные операции могут комбинировать движения: рефакторинг обычно использует C для фиксации текущего контракта, затем A для изменения и пересборки; исправление бага — D для локализации и A для изменения подтверждённого поведения; миграция — C + A.

**Трек B** не является четвёртым движением содержания. Это отдельный мета-трек: он меняет правила самой документационной обвязки.


## 1. Трек A — новое содержание, сверху вниз

Цель: превратить подтверждаемое намерение в проверяемую спецификацию и реализацию.

`design/human/` → `design/floor1/` → `design/floor2/` → декомпозиция → `src/` → проверка.

### A1. Видение → этаж 1

Вход: новый фрагмент видения или решения человека.

Передать: `AGENTS.md`, соответствующий `design/human/*`, текущие `design/floor1/*`, `design/trace/` и `design_docs/01–02,07`.

Промпт: `design_docs/prompts/p-translate-vision.md` или `p-create-story.md`.

Выход: `draft`-глоссарий/истории, открытые вопросы и обновлённое покрытие.

### A2. Этаж 1 → этаж 2

Вход: согласованный этаж 1.

Передать: `AGENTS.md`, `design/human/`, `design/floor1/`, `design/trace/`, `design_docs/00–04,07–09`, шаблоны второго этажа и `p-start-floor2.md`.

Промпт: `design_docs/prompts/p-start-floor2.md`.

Выход: **только план** `US → candidate REQ → candidate CON/diagram`, список точных путей, блокирующие вопросы. Рабочие файлы не создаются.

После решения блокирующих вопросов:

Промпт: `design_docs/prompts/p-create-requirement.md`.

Выход:
- `design/floor2/requirements/REQ-NNN.yaml`;
- применимые `design/floor2/constraints/CON-NNN.yaml`;
- применимые `design/floor2/diagrams/comm/COMM-NNN.yaml`;
- применимые `design/floor2/diagrams/string/STR-NNN.yaml`.

### A3. Этаж 2 → реализация
Декомпозиция и выбор маршрута описаны в Треке E (§5). После реализации: `p-review.md` и валидатор.

## 2. Трек B — изменение самой обвязки

Цель: менять `AGENTS.md`, `design_docs/`, шаблоны, промпты, валидатор или структуру каталогов.

Промпт: `design_docs/prompts/p-evolve-process.md`.

Порядок:

1. Зафиксировать воспроизводимую проблему.
2. Найти правило и все зависимые файлы.
3. Предложить минимальный согласованный дифф.
4. После решения изменить правила, шаблоны, промпты, проверки и README согласованно.
5. Запустить валидатор и затронутые проверки.
6. Записать смысл изменения в `CHANGELOG.md`, а существенное решение — в `design/trace/nav-log.yaml`.

## 3. Трек C — внедрение документации в существующий проект, снизу вверх

Вход: `src/` содержит код, а документация отсутствует или неполна.

**Шаг 0. Граница внедрения.** Человек указывает, какие модули покрываются документацией, а какие остаются `legacy`.

**Шаг 1. Извлечение.** Промпт `design_docs/prompts/p-adopt-existing.md` читает код и тесты и создаёт только `draft`-артефакты: глоссарий, истории, требования и контракты, которые действительно наблюдаются.

**Шаг 2. Подтверждение.** Человек подтверждает/исправляет смысл. Только после этого артефакт получает `confirmed`.

**Шаг 3. При необходимости — аудит.** Если документация существовала до внедрения, запустить Трек D и получить `design/trace/discrepancies.yaml`.

**Шаг 4. Разрешение.** Для каждого рассогласования человек выбирает: изменить код, изменить документацию или принять отклонение (`accepted_deviation`).

Код на шаге извлечения не изменяется.

## 4. Трек D — оценка рассогласования

Вход: `design/` и `src/` существуют, но есть suspected drift, баг или параллельные изменения.

Промпт: `design_docs/prompts/p-assess-discrepancy.md`.

Результат: `design/trace/discrepancies.yaml`, где каждая запись содержит `id`, `artifact`, `code_location`, `expected`, `actual`, `severity` и `status`.

Далее человек:

- меняет код → `resolved`;
- меняет документацию → `resolved`;
- принимает отклонение → `accepted_deviation` + `rationale`.

При изменении покрытия обновляется `design/trace/coverage.yaml`.

## 5. Трек E — декомпозиция

Промпт: `design_docs/prompts/p-decompose.md`.

Перед декомпозицией выбирается один из маршрутов:

- **D1** — новый модуль из подтверждённого требования, сверху вниз;
- **D2** — извлечение модуля из существующего кода, снизу вверх;
- **D3** — разделение модуля на подмодули на том же уровне;
- **D4** — выделение модуля в подпроект `subs/<name>/`.

Если контракт отсутствует для D2/D3, сначала выполняется Трек C для его извлечения и подтверждения.

## 6. Контекст между диалогами

Новый диалог получает не всю историю чата, а:

- цель и выбранный трек;
- релевантные рабочие файлы;
- соответствующие правила и шаблоны;
- открытые вопросы и записи `design/trace/`;
- ограничения на изменение файлов;
- согласованный план предыдущего шага.

В конце диалога LLM возвращает изменённые пути, смысл изменений, проверки, открытые вопросы и следующий шаг. Источник истины — рабочие файлы и Git, а не резюме модели.

## 7. Критерий достаточной определённости

Маршрут определён, если новый диалог без скрытого контекста может ответить:

1. какие файлы прочитать;
2. какой промпт запустить;
3. какие пути разрешено создать/изменить;
4. каким наблюдаемым критерием проверить результат.

Если хотя бы один ответ отсутствует, это дефект процесса и кандидат на Трек B.
