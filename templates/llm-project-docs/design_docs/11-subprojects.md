# 11. Подпроекты и владение кодом

## 1. Принцип владения

Физический файл/каталог редактируется на том уровне, которому он принадлежит. Вышестоящий уровень использует симлинк вместо копии, когда это совместимо с инструментами проекта.

`subs/<name>/src/` содержит реальные файлы подпроекта. Родительский `src/` может содержать симлинк на каталог/файл подпроекта.

## 2. Структура

```text
subs/<name>/
  design/
  src/
  subs/
```

`design_docs/` не дублируется внутри подпроекта: мета-правила едины и находятся в корне.

`design/` подпроекта может ссылаться на родительскую документацию для контекста относительными ссылками; не создавай копии родительских артефактов.

## 3. Симлинки в `src/`

Если модуль делегирован подпроекту, родительский `src/` содержит симлинк на `subs/<name>/src/` или на конкретный файл. Агент не создаёт копию вместо симлинка.

Перед изменением структуры проверь поддержку симлинков Git, ОС и системы сборки. Если симлинки неприемлемы, остановись и предложи альтернативу вместо молчаливой замены копированием.

## 4. Манифесты и тесты

Манифест (`Cargo.toml`, `package.json`, `CMakeLists.txt` и аналогичный) принадлежит уровню, определяющему сборку. Не создавай вторую независимую копию только ради контекста.

### Вариант 1 — минимальный

Если подпроектов ≤ 2 и они редко меняются независимо, тесты/сборка запускаются на уровне родительского манифеста. В подпроекте допустима тонкая обёртка (`Makefile`, `justfile`, `test.sh`), делегирующая команду наверх.

### Вариант 2 — независимые пакеты/workspace

Если подпроектов >= 3 или им нужна независимая сборка/версионирование, человек может выбрать нативный механизм workspace/monorepo. Для Rust это обычно Cargo workspace. Это отдельное архитектурное решение, а не автоматическое правило симлинков.

В `subs/<name>/design/` фиксируется фактическая команда проверки и уровень, на котором она выполняется.

## 5. Зависимости

Если A зависит от B, A использует опубликованный/подтверждённый интерфейс B. A не редактирует код B. Контракт B, видимый из A, описывается как внешняя зависимость в `floor2` документации A.

## 6. Граница видимости

Документация подпроекта должна быть достаточной для его разработки без чтения внутренней реализации соседних подпроектов. Зависимости выражаются через контракты, типы и интерфейсы. Если разработка требует постоянного чтения чужого `src/`, это сигнал пересмотреть границу или контракт.
