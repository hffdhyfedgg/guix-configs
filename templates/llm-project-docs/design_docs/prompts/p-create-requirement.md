# Промпт: создать требования второго этажа

## Прочитать перед работой

- `AGENTS.md`
- `design_docs/00-principles.md`, `design_docs/02-stories.md`, `design_docs/03-requirements.md`, `design_docs/04-diagrams.md`, `design_docs/07-communication.md`, `design_docs/08-verification.md`, `design_docs/09-naming.md`
- `design/floor1/glossary.yaml`, релевантные `design/floor1/stories/US-*.yaml`, `design/trace/coverage.yaml`, `design/trace/nav-log.yaml`
- шаблоны `design_docs/templates/requirement.yaml`, `constraint.yaml`, `comm-diagram.yaml`, `string-diagram.yaml`

## Задача

Работай только по фактическому содержимому переданных файлов. Не выдумывай решения человека, детали реализации, результаты проверок или термины, которых нет в источниках.

1. Сопоставь истории с кандидатами требований. `REQ` может покрывать несколько историй; не создавай отдельный `REQ` на каждую историю автоматически.
2. Для каждого `REQ` укажи `type`, точный `dom`, `entities`, `actions`, `source_refs`, приоритет и аргументированные связи `covers` (`precondition`, `postcondition` или `both`). Каждый аргумент должен объяснять, как именно требование обеспечивает выбранную часть истории.
3. Создай файл требования строго по пути `design/floor2/requirements/REQ-NNN.yaml` на основе `design_docs/templates/requirement.yaml`.
4. Для каждого независимо проверяемого условия оцени, можно ли сформулировать сигнатуру и предикат. Если да, создай отдельный `CON` по пути `design/floor2/constraints/CON-NNN.yaml` на основе `design_docs/templates/constraint.yaml`; добавь его ID в `formalization.constraints` соответствующего `REQ`. Не создавай `CON`, если условие остаётся только пожеланием или неоднозначной фразой.
5. Для структурных отношений создай `COMM` по пути `design/floor2/diagrams/comm/COMM-NNN.yaml`, только если нужна проверка согласованности путей. Для композиции действий создай `STR` по пути `design/floor2/diagrams/string/STR-NNN.yaml`, только если схема добавляет полезную точность. В остальных случаях оставь `diagrams: []` и объясни причину.
6. Термины, от которых зависит смысл, но которые не определены, перечисли в `unresolved`. Не маскируй их через `primitive: true`.
7. Для `CON` укажи witness/counterexample, только если можешь привести осмысленные примеры; иначе объясни невозможность. Укажи фактический способ проверки и статус `not_run`, пока он действительно не выполнен.
8. Сохрани статусы `draft`, если нет подтверждения. Подтверждение формулировки не означает техническую проверку `passed`.
9. Проверь покрытие, связанные записи и причинные зависимости. Для решений/конфликтов, которые существенно влияют на архитектуру, предложи запись в `design/trace/nav-log.yaml`.
10. После изменений запусти `python design_docs/scripts/validate_docs.py`, если среда позволяет. Чётко сообщи, какие проверки реально выполнены.

## Выход

Перечисли созданные/изменённые пути. Для каждого `REQ` покажи покрываемые истории, открытые вопросы и способ проверки. Для каждого `CON` покажи родительский `REQ`, сигнатуру, предикат и метод проверки. В конце дай покрытие по историям, список блокирующих решений и результаты валидации. Не заявляй, что этаж 2 полон, если есть непокрытые `must`-истории или неразрешённые блокирующие вопросы.
