# Документация проекта с LLM

Этот комплект разделяет **правила работы над проектом** и **документацию конкретного проекта**.

- `design_docs/` — мета-уровень: правила, шаблоны, промпты и валидатор. В обычной работе он считается неизменяемым; изменения выполняются только по Треку B.
- `design/` — документация конкретного проекта: исходное видение, этажи, след решений и покрытие.
- `src/` — код текущего уровня проекта.
- `subs/` — отдельные подпроекты с собственной документацией и кодом.

## Структура

```text
design_docs/          # правила процесса, шаблоны, промпты, проверки
  00-principles.md … 11-subprojects.md
  templates/
  examples/
  prompts/
  scripts/
design/              # содержание конкретного проекта
  human/
  floor1/
  floor2/
  trace/
src/                  # код текущего уровня
subs/                 # подпроекты
  <name>/
    design/
    src/
    subs/
```

## Главные треки: что и когда отправлять LLM

### Трек A — новый проект / изменение продукта, сверху вниз

**Когда:** появляется новое видение, функция, пользовательская потребность или требование.

**Что дать LLM:** `AGENTS.md` + релевантные файлы `design/human/` + текущий этаж + соответствующий промпт.

**Маршрут:**

`видение → floor1 → floor2 → декомпозиция → src → проверка`

1. Новое видение: `design_docs/prompts/p-translate-vision.md`.
2. Новая/изменённая история: `design_docs/prompts/p-create-story.md`.
3. После готовности этажа 1: `design_docs/prompts/p-start-floor2.md`. Это **только планирование**: LLM строит `US → candidate REQ → candidate CON/diagram`, но не пишет второй этаж.
4. После согласования плана: `design_docs/prompts/p-create-requirement.md`. Он создаёт `REQ` в `design/floor2/requirements/`, применимые `CON` в `design/floor2/constraints/` и диаграммы только при необходимости.
5. После согласования требований: `design_docs/prompts/p-decompose.md` — выбрать маршрут D1–D4 и декомпозировать.
6. `design_docs/prompts/p-review.md` + `python design_docs/scripts/validate_docs.py` — проверить результат.

**Что передавать между диалогами:** не всю историю чата, а актуальные файлы, согласованный план, открытые вопросы и краткое резюме предыдущего шага. Источник истины — файлы Git.

### Трек B — изменение самой обвязки

**Когда:** LLM систематически не знает, куда писать артефакт; правила, шаблон, промпт и валидатор расходятся; процесс требует нового маршрута; структура каталогов мешает работе.

**Что дать LLM:** воспроизводимый пример сбоя + `AGENTS.md` + затронутые `design_docs/` + `STRUCTURE.md`/`CHANGELOG.md` и соответствующие тесты.

**Промпт:** `design_docs/prompts/p-evolve-process.md`.

**Правило:** сначала план изменения и список зависимых файлов, потом согласование, затем связанный дифф. После изменения проверить правила, шаблоны, промпты, валидатор и README. Изменение обвязки не превращается автоматически в продуктовый `REQ`.

### Трек C — внедрение документации в существующий код, снизу вверх

**Когда:** `src/` уже существует, а контракты и документация отсутствуют или неполны.

**Что дать LLM:** `AGENTS.md`, целевой путь в `src/`, существующую документацию (если есть), тесты и соответствующий контекст сборки.

**Промпт:** `design_docs/prompts/p-adopt-existing.md`.

**Маршрут:**

`src → draft contract → подтверждение человека → documentation`

LLM извлекает только наблюдаемое из кода и тестов, создаёт `draft`; человек подтверждает смысл; затем артефакты становятся `confirmed`. Код на этом треке не изменяется.

### Трек D — аудит рассогласования

**Когда:** документация и код уже существуют, но есть подозрение на drift, баг или параллельные изменения.

**Что дать LLM:** `design/`, `src/`, конкретный модуль/REQ/CON при необходимости.

**Промпт:** `design_docs/prompts/p-assess-discrepancy.md`.

**Результат:** `design/trace/discrepancies.yaml` с `DISC-NNN`. LLM только фиксирует `expected`/`actual`; человек решает, менять код, документацию или принять отклонение.

### Какой трек выбрать

| Ситуация | Трек | Первый промпт |
|---|---|---|
| Новая функция / новое видение | A | `p-translate-vision.md` |
| После готовности floor1 | A | `p-start-floor2.md` |
| Создание REQ/CON | A | `p-create-requirement.md` |
| Новая декомпозиция (сверху вниз) | A → E | `p-decompose.md` |
| Декомпозиция существующего модуля | C → E | `p-adopt-existing.md`, затем `p-decompose.md` |
| Выделение модуля в подпроект | E | `p-decompose.md` (маршрут D4) |
| Существующий код без контракта | C | `p-adopt-existing.md` |
| Код и docs расходятся | D | `p-assess-discrepancy.md` |
| Нужно изменить правила LLM/структуру docs | B | `p-evolve-process.md` |

Одна задача может затрагивать несколько треков. В таком случае явно разделяй их: например, **D** обнаруживает рассогласование, а **A** исправляет подтверждённое требование; **B** меняет сам процесс только если обнаружен дефект процесса.

## Быстрый запуск после этажа 1

1. Передай LLM `AGENTS.md`, `design/human/`, `design/floor1/`, `design/trace/`, правила `design_docs/00–09`, шаблоны и `design_docs/prompts/p-start-floor2.md`.
2. Попроси выполнить **только планирование** и вернуть матрицу `US → candidate REQ → candidate CON/diagram`.
3. Ответь на блокирующие вопросы и скорректируй план.
4. Передай тот же вход + согласованный план в `p-create-requirement.md`.
5. Проверь `design/floor2/`, затем `p-review.md` и валидатор.
6. Только после этого переходи к `p-decompose.md` и к `src/`.

## Правило для LLM

Если неясно, **что создавать, где создавать или какой маршрут применять**, LLM должна остановиться на плане и задать вопрос, а не угадывать. Подтверждение человека не равно технической верификации.

## Проверка

```bash
python design_docs/scripts/validate_docs.py
```

Валидатор проверяет структуру, YAML и часть ссылок. Он не доказывает полноту требований, корректность архитектуры или соответствие кода намерению пользователя.
